# WeWave website — working rules

Read this before changing anything. It exists because this project has been
built across many AI sessions, and the failures that actually happened here are
recorded below so they don't happen again.

## The one rule

**The site is designed and working. Do not redesign it.** Colours, typography,
spacing, layout, sections, copy, animations, timing, hover and touch behaviour,
navigation, branding and logos are all settled. Change them only when the user
asks for that specific change, or to fix a confirmed bug.

If you are unsure whether an edit could alter behaviour, don't make it. Say what
you would change and why, and let the user decide.

## What this is

A static site — plain HTML, CSS and JavaScript. **No framework, no bundler, no
package manager, no TypeScript, no dependencies.** Do not introduce any. There
is no `npm install`, no build step for the app itself, and nothing to compile.

In front of the static files sits a Cloudflare Worker (`worker/index.js`) that
adds a booking API backed by D1.

### `dist/` will catch you out

Cloudflare deploys `dist/`, so it is committed — but it is *output*. It is a
copy of the source files. Edit `dist/` and your change goes live once, then
vanishes on the next build. Edit the source and forget to rebuild, and nothing
happens at all.

**Always: edit source → `python tools/build_dist.py` → commit both.**

## How the engine works

Native scroll drives a virtual timeline `0..1`. A lerped copy of it
(`smooth += (target - smooth) * 0.085`) animates seven `position:fixed`
full-viewport stages, interpolates the palette into CSS custom properties on
`:root`, and shapes a canvas ribbon. One `requestAnimationFrame` loop drives
everything, so every motion shares one clock. A `.driver` div of `900vh`
provides the scroll height.

Stages are not a scrolling document. They are fixed layers crossfaded by
progress. Do not "fix" this by making them scroll.

## Do not touch casually

These are tuned by eye. No test will catch a regression; only the user's eye
will, and by then it is live.

- `STAGES` start/end windows — `js/main.js`
- `PALETTE` stops — `js/main.js`
- the `0.085` lerp constant
- `SPRING` / `DAMP` lamp values
- `ribbonX()` maths
- stage/lamp CSS transition durations

## Traps that have already bitten this project

**An inline `<script>` will not run.** Every response carries a
Content-Security-Policy with `script-src 'self'` and no `'unsafe-inline'`, so
a `<script>` block written directly into a page is silently blocked -- no
error on the server, just a dead page. Put the code in a `.js` file and load
it with `src`. This is why `admin/index.html` and `admin/analytics/index.html`
have an `app.js` beside them instead of the inline blocks they used to carry.
`style-src` still allows inline styles, deliberately: the stage engine writes
them every frame.

Everything the page may load is listed in `CSP` in `tools/build_dist.py`. A
new external origin -- a font host, an embed, an analytics vendor -- has to be
added there or it will be blocked.

**One missing element used to blank the whole site.** `js/main.js` is a single
non-module script: an uncaught error anywhere stops everything after it. Start-up
DOM lookups are now guarded — keep it that way. When you add a new
`$('#something')`, guard it, or you reintroduce the failure.

**Renaming a constant broke everything silently.** `node --check` passes on a
`ReferenceError`; it only checks syntax. After editing `js/main.js`, load the
page and confirm it renders.

**Declaration order matters.** Everything is module-scope `const`. A `const`
read above its declaration throws at runtime, not at parse. Declare shared flags
(`LIGHT`, `TOUCH`, `SMALL`) at the top.

**Script order matters too.** These are classic scripts, so a top-level `const`
in one is visible to the next. `js/meeting-modal.js` uses `$` and `$$` from
`js/main.js` and must load after it. Do **not** redeclare `$` or `$$` there —
a second top-level `const $` is a SyntaxError across scripts, not a shadow.

**The 900px breakpoint lives in two languages.** `SMALL` in `js/main.js` and
`@media (max-width:900px)` in `css/style.css`. Change one, change the other, or
the mobile render path and the mobile layout disagree.

**Never declare a background-image for a file that might not exist.** The
browser re-requests a missing background on every repaint. That is why
`css/service-shots.css` is generated and only ever names files actually on disk.

## Testing, and why screenshots lie here

**The preview pane freezes `requestAnimationFrame` and CSS transitions.** Values
read mid-transition come back as their start value, and stages never advance.
This has produced false failures repeatedly. Trust:

- computed styles read *after* disabling transitions
- `document.elementFromPoint` for hit-testing
- DOM state and network logs

Do not trust a blank screenshot as evidence of a bug.

## Adding things

**A new service:** add it to the `SERVICES` data in `tools/build_services.py`,
add a card in `index.html`, drop a `<slug>.jpg` in `assets/services/`, then run
`build_services.py`, `build_shots.py`, `build_dist.py`. Never hand-write a page
in `services/`.

**A service image:** drop the file in `assets/services/` named by slug, run
`python tools/build_shots.py`. No code change.

**Retiring a service** touches six places, and missing one leaves a dead link
or an orphan page: the card in `index.html`, the checkbox in the booking
modal (same file), the entry in `tools/build_services.py`, the slug in
`tools/build_shots.py` and `tools/make_service_art.py`, then **delete**
`services/<slug>.html` and `assets/services/<slug>.jpg` -- the generators do
not remove files they no longer produce. Renumber what is left: the card
numbers and `num=` must agree and run from 01 with no gaps. Then run all
three builds. Historical bookings in D1 keep the old service names, and the
admin panel still shows them; that is correct, it is what the client asked
for at the time.

**Mobile behaviour:** reuse the existing per-frame rail pass rather than adding
a scroll listener or a second rAF loop. Cache layout reads at resize — never
call `getBoundingClientRect()` per frame.

**Never move the services rail directly.** Its offset is derived from the
scroll timeline every frame, so anything that sets `rail.style.transform` is
overwritten on the next frame. To move it, work out the progress value that
produces the position you want and call `scrollToProgress()` — that is what the
nav links and the sideways swipe both do, which is why they cannot disagree.
`easeIOInv()` exists to convert a wanted rail offset back into progress.

## Analytics

`js/analytics.js` collects behaviour into the D1 tables `a_event` / `a_session`
and the dashboard reads it at `/admin/analytics`. Things worth knowing:

- It reads the page and never writes to it. It is an IIFE declaring nothing at
  top level, and every entry point swallows its own errors — keep it that way.
- Section views come from a `MutationObserver` on the `.stage` class list that
  `renderStages()` already toggles. Do not add a scroll listener or a second
  rAF loop for this.
- Scroll depth is `scrollY / scrollable()`, i.e. progress along the timeline,
  not a document position. `STAGE_AT` in the dashboard mirrors `STAGES` — if you
  retune a stage window, update it there too or the heatmap preview parks at the
  wrong place.
- The first stage is keyed `manifesto` but reads **About us** on the page. The
  key is what `a_event` rows, `STAGE_AT` and `.stage-manifesto` all use, so
  renaming it would orphan the history. Change `label` in `STAGES`, the nav
  link and the eyebrow -- never the key.
- `?wwtest=1` marks a browser as a test client. Those rows carry `is_test = 1`
  and never appear in the live figures.
- Events are whitelisted by pattern, not by list, so `window.wwTrack('MY_EVENT',
  {...})` works without a Worker deploy.

## The case study simulator

`/admin/case-studies` builds hypothetical Meta-Ads-shaped case studies for
client presentations. **It has never been connected to Meta and must not be.**
Nothing in it fetches ad data, asks for platform credentials, or presents its
figures as reported performance — the `DEMO · CASE STUDY DATA` badge and the
notice bar are the standing statement of that, and they stay, including in
presentation mode. Keep it that way.

It is the one part of the project that uses **ES modules** (`<script
type="module">`) and a **light** palette. Both are deliberate: the module
boundary is what keeps the arithmetic out of the UI, and a table this dense is
unreadable on the dark green. It loads none of the site's CSS or JS and exports
none, so it cannot affect any other page.

| File | What's in it |
|---|---|
| `engine.js` | The data model and **every formula**. Pure — no DOM, no network |
| `presets.js` | Nine starting templates and the demo library |
| `store.js` | D1 via the admin API, mirrored to `localStorage` |
| `charts.js` | Hand-rolled SVG charts — no library, keep it that way |
| `app.js` | The interface. Renders and wires; contains no arithmetic |

Things that will catch you out:

- **Put no maths in `app.js`.** Every figure comes from `engine.js`, which is
  why the interface cannot show two numbers that disagree. `tools/test_case_engine.mjs`
  guards it; a formula added in the UI is guarded by nothing.
- **A node with children keeps `own` at zero.** That single rule makes totals
  unambiguous. Editing a parent redistributes across descendants rather than
  storing a second copy — see `setCore` and `pushOwnDown`.
- **`node --check` does not check these files.** It parses `.js` as CommonJS and
  silently passes anything with `export` in it. Use
  `node --experimental-vm-modules` with `vm.SourceTextModule`, or just load the
  page.
- **`.table-scroll` sets `overflow-x:auto`, which makes it a scroll container on
  both axes.** So `thead`'s sticky `top` is relative to *that box*, not the
  viewport. Any non-zero value parks the header on top of the first row. It is
  `top:0` for that reason.
- **`--topbar` is measured, not hard-coded.** The sidebar sticks below the top
  bar, and the bar wraps on narrow screens. A zero measurement is discarded —
  while the token gate is up the bar has no height.
- **Row order is cached on purpose** (`sortRows`). Re-sorting on every render
  makes the row you are editing jump away the moment you change its value.
  Order is recomputed on sort, level, search, filter and structure changes only.
- **Each core metric gets its own daily curve** in `series()`. With one shared
  curve every ratio — ROAS, CTR, CPC — comes out a dead flat line.
- Charts are a *modelled* daily shape over period totals, never per-day input,
  and the UI says so. Each series still sums to exactly the headline figure.

## The work showcase

`/services/web-development` carries a segmented wheel of the sites we have
built. `js/showcase.js` draws it; the projects come from the `folio` list in
`tools/build_services.py`. Any service with a `folio` gets one.

- **There is no second copy of the data.** The script reads the `.folio`
  links the page already renders, including their `data-preview` and
  `data-thumb` attributes. Edit `folio` and both the wheel and the plain grid
  change together.
- **The plain grid is the fallback, and the script hides it** by putting
  `is-replaced` on its section once the wheel is known to have built. Without
  JavaScript the grid is simply what you see. Delete that one line if you
  would rather show both.
- **`preview` is measured, not guessed.** A site sending `X-Frame-Options` or
  `frame-ancestors` cannot be embedded by anyone. ZREX, Valle and Laro all
  do, so they are `thumb`; InstaPro, Iris, Saffa and Royal Watch do not, so
  they are `live` and were each confirmed rendering. Check a new one before
  setting `live` -- and note some servers refuse HEAD, so use GET:
  `curl -s -D - -o /dev/null -L <url> | grep -iE "x-frame-options|content-security-policy"`
- **Thumbnails are real screenshots**, captured by pointing a browser at the
  live site and running `python tools/save_folio_shot.py <slug>`. A stock
  photo or a drawn browser window would be a lie about the work.
- **`frame-src https:` is in the CSP for this.** Without it `frame-src` falls
  back to `default-src 'self'` and every preview is blocked in silence.
- Frames are built on first selection and kept, so moving back and forth
  across the wheel never reloads a client's site. A site that is `live` but
  stops answering falls back after six seconds rather than showing a blank.
- `--sc-scale` is measured in JS, not hard-coded: the frame renders at
  1280px so previews show the desktop layout, and the factor that shrinks it
  to the panel comes from the panel's own width.
- The entrance uses `void panel.offsetHeight` rather than
  `requestAnimationFrame`, which does not fire in a background tab and would
  strand the panel at opacity 0.
- **Focus events do not fire on SVG elements.** `wedge.focus()` moves
  `document.activeElement` -- Enter and the arrow keys work off it -- but no
  `focus` or `focusin` event is dispatched, so a listener on the wedge never
  runs. Opening the wheel left the panel blank for exactly this reason. Every
  path that moves focus now calls `select()` itself, and a document-level
  `keyup` on Tab catches a tab in from outside. Do not put behaviour on an
  SVG element's focus event.
- **No `loading="lazy"` on the fallback screenshot.** The image is only
  created when its segment is selected, which is already the lazy part; the
  attribute added a second viewport-based gate and the thumbnails silently
  never loaded at all.
- The old `iris-eg.net` is dead. The live site is `iris-eg.org` -- a
  different domain, not a redirect.

## The API

Both public routes are rate limited, and the admin gate throttles failures.
All three share `submit_log`, keyed by `SHA-256("<bucket>|<address>")` so no
address is stored and one bucket's traffic cannot count against another's.

| Bucket | Limit | Why |
|---|---|---|
| `meeting` | 5 / 10 min | A human books once; the mailto fallback catches anyone blocked |
| `analytics` | 240 / 5 min | `/api/a` is unauthenticated and writes up to 61 rows a call, into the same database the bookings use |
| `adminfail` | 10 / 15 min | The token is the only thing in front of every lead's phone number |

**The admin bucket counts failures only.** `overRateLimit(..., record=false)`
checks without writing a row; `noteAuthFailure` writes one. Recording every
admin call instead would let the analytics dashboard's own realtime polling
throttle the owner out of their own panel within a minute -- that bug existed
for about twenty minutes and `tools/test_api.py` has a check for it.

On top of the per-address limit, `worker/analytics.js` refuses ingest past
`DAILY_EVENT_CAP` events in a UTC day, so behaviour data can never spend the
D1 write allowance that the booking form needs.

`meetings` and `submit_log` build themselves on first use (`ensureCoreSchema`),
the same way the analytics tables do. They used to exist only in production,
created by hand, so a restored database or a local `wrangler dev` answered the
booking form with `no such table: meetings`. `schema/meetings.sql` holds the
same DDL in readable form.

`GET /api/meetings` and `PATCH /api/meetings/:id` require
`Authorization: Bearer <ADMIN_TOKEN>` and fail closed when the secret is unset.

`/api/cases` (list) and `/api/cases/:id` (GET / PUT / DELETE) are the case study
store, on the same token and the same fail-closed check. There is deliberately
**no public read path** — case studies are internal working documents, and
sharing one is done through presentation mode, print-to-PDF, or an export file.

`ADMIN_TOKEN` is a Worker secret. **Adding a secret in the Cloudflare dashboard
creates a new version but does not deploy it** — you must promote that version,
or it silently has no effect. This cost an hour once.

`LEAD_WEBHOOK_URL` is an optional second secret. Unset, a booking is stored
and **nobody is told** -- the only way to find out is to open `/admin`. Set it
and `notifyLead` posts a JSON summary after the response, via `ctx.waitUntil`,
so a slow webhook cannot delay or fail a captured lead. It deliberately omits
the visitor's phone number and message; see `README.md`.

Never log, echo, or commit either secret. `.dev.vars` is gitignored; keep it
so. `.dev.vars.example` is committed and must never hold a real value.

## Before saying you are done

There is no type checker, linter or test suite to run. So:

```bash
python tools/build_dist.py          # rebuild the deploy folder
node --check js/main.js             # syntax only — not enough on its own
node tools/test_case_engine.mjs     # 57 checks on the case study arithmetic
python tools/test_api.py            # 46 checks on the API -- needs the Worker running
```

`tools/test_api.py` wants `npx wrangler dev --local --port 8899` in another
terminal. `--local` needs no Cloudflare login and touches nothing remote. It
is the only coverage the lead pipeline has, so run it before any deploy that
touches `worker/`.

Then actually load the page and confirm:

1. it renders (not blank)
2. no console errors, no 404s
3. scrolling moves through all seven stages
4. hovering a service card reveals its image, and leaving clears it
5. the booking modal opens, validates, and closes
6. the lamp lights on hover and goes fully dark on leave

After deploying, verify against the live URL rather than assuming the build
succeeded. Cloudflare's build queue is sometimes slow, and a queued build looks
identical to a finished one from here.

## Known and deliberate

- `MEETING_MAILTO` lives in `js/meeting-modal.js`, not `main.js`. It is the
  address the modal falls back to when the API is unreachable — confirm it is
  the right inbox.
- The site is closed to search engines on purpose. `SITE_URL` at the top of
  `tools/build_dist.py` is the single switch: fill it in and the same build
  emits canonical URLs, Open Graph and Twitter cards, and a sitemap, and flips
  robots and the noindex header. `/admin` stays excluded either way. The
  Open Graph image still falls back to the logo mark rather than a real
  1200x630 card.
- All five service images load eagerly (190KB). This line claimed ~115KB when
  there were nine of them and the real figure was 334KB; it is measured now.
  Accepted: it keeps the first hover instant.
- The eight client logos ship as lossless WebP with a PNG fallback through
  `image-set()` -- 368KB down to 280KB, and `tools/build_client_webp.py`
  refuses to write a file that is not pixel-identical to its PNG. Re-run it
  after changing any logo.
- `build.py` and `wewave-standalone.html` build a single-file copy for sharing
  outside a web host. Obsolete now the site is deployed, kept pending the user's
  decision.
